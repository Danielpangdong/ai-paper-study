递归式语言模型（Recursive Language Models）：让 LLM 自己「读」无限长的提示

把超长上下文当作一个外部 Python 环境，让模型用代码去检索、切片、再递归地调用一个「子自己」—— 这是 MIT CSAIL 在 2025 年底放出、并在 2026 年初被 Prime Intellect、DeepLearning.AI The Batch、InfoQ 等 相继冠以「2026 范式」之名的一篇推理时（inference-time）新工作。

一句话讲清楚 RLM 是什么

不是把更长的 prompt 塞进模型，而是把 prompt 当成一段可执行环境里的变量，让模型用代码去「主动阅读」它， 必要时再调用一个「自己」去看其中一小段——递归下去，直到答案收敛。

“RLMs treat long prompts as part of an external environment and allow the LLM to programmatically examine, decompose, and recursively call itself over snippets of the prompt.” — 摘要原文

这条思路的厉害之处在于：它不依赖更大的上下文窗口、不做有损摘要， 也不需要改模型权重——它只改变「推理时」如何把上下文喂给模型， 因此可以叠加在 GPT-5、Qwen3 等几乎任何前沿 LLM 之上。

机制图解：根模型 → Python REPL → 子 LLM

最小可运行心智模型（伪代码）

论文给出的核心思路可以用十几行伪代码表达——这正是「The Bitter Lesson」式的简洁：

# 1) 把超长输入塞进一个变量，不直接拼进 prompt context = load_input() # 例：1000 篇文档拼接、100k+ tokens # 2) 给根模型一个带 REPL 工具的轻量系统提示 system = """你可以使用 python(code) 工具。 context 已是变量；用切片/正则/统计去看它。 若需要让另一个 LLM 看其中一段，调用 sub_llm(snippet, query)。 每轮只能输出一个 python(...) 调用或最终答案。""" # 3) 根模型自驱循环：读 → 写代码 → 看结果 → 决策 while True: action = root_llm(system, history) if action.is_final_answer: return action.text obs = python_exec(action.code, env={"context": context, "sub_llm": sub_llm}) history.append((action, obs))

关键点：context 永远不出现在 root_llm 的上下文窗口里； 它只通过 python(...) 间接被「触摸」。这就是 RLM 能突破窗口约束的根本原因。

关键基准：BrowseComp-Plus 多文档检索 QA

1000 文档规模下的稳健性

在 BrowseComp-Plus 上抽样 20 条 query，分别给 10 / 50 / 100 / 1000 篇文档作为输入， 只有 RLM(GPT-5) 在文档量达到 1000 时仍维持接近满分； 普通 GPT-5 直接被上下文长度卡住，摘要式 agent 则因有损压缩明显下滑。

BrowseComp+ 直接对比（100 文档）

关键基准：OOLONG（长上下文综合）

同样的小模型，套上 RLM 后逼近大模型水平

OOLONG 上下文长度约 132k tokens。RLM-Qwen3-8B 在三类长上下文任务的平均分上比裸 Qwen3-8B 提升 28.3%， 甚至接近原生 GPT-5 的成绩——意味着「会管理上下文」的 8B 模型，可以局部追上一个体量大它一两个数量级的旗舰。

与传统长上下文方案的横向对比

方案 上下文上限 是否有损 是否需训练 对前沿模型的可叠加性 实测表现（长 QA）
原生超长上下文（如 1M tokens 模型） 受架构 / 显存约束 无损 需要 差（绑死单一模型） 随长度急剧衰减
摘要 / 压缩 agent ≈ 任意 有损 否 强 关键细节易丢失

第一性原理：为什么这条路是 2026 的一个「正确方向」

它对了什么

  • 把「读上下文」变成一种行为，而非被动塞入注意力——更接近「人类读长文档」。
  • 无损 + 无需重训，天然继承前沿模型的能力上限。
  • 可作为环境训练：Prime Intellect 的 RLMEnv 已能用 RL 直接在 RLM 脚手架内学习， 符合 Sutton《The Bitter Lesson》——让算力与搜索去赢。
  • 可组合性强：DSPy 已把 RLM 收为内置 module，未来与工具调用 / 多智能体天然融合。

必须正视的局限

  • 延迟更高：每一步都要执行 Python，并可能产生若干 sub-LLM 调用，整体串行链路变长。
  • 调度策略学习未完善：「何时切片、何时递归、何时停止」目前主要靠提示工程驱动。
  • 沙盒安全：把模型生成的代码直接 exec 到上下文上，需要严格隔离与配额。
  • 评测覆盖偏窄：现有结果集中在长 QA / 多文档检索，对长代码、法律文书等场景仍待补全。

工程复制路径（不重复造轮子）

  • 📦 官方实现：alexzhang13/rlm（GitHub），plug-and-play 推理库，已支持多种沙盒。
  • 🧰 DSPy 模块：dspy.RLM，可直接作为可组合 module 与 ReAct / RAG 串联。
  • 🌐 训练环境：Prime Intellect 在 Environments Hub 提供多个 RLM-based env，配合 prime-rl 直接训。
  • 🧪 社区复现：Node/TS 版（hampton-io/RLM）、轻量 REPL 版（fullstackwebdev/rlm_repl）、 快速版（avbiswas/fast-rlm）等已可读源码学习。
  • 🧭 第一步建议：先在自有「多文档客服检索」「长代码 PR Review」等场景上跑一个最小 RLM 原型， 用 GPT-5 或自家最强模型作 root，统计准确率与单 query 成本——别一开始就训。

给中国开发者的 5 条带走

  1. 长上下文不是「模型问题」，而是「调度问题」。模型大小没变，效果可以变。
  2. RLM 是一种推理范式，不是新模型——可以套在任何足够强的 root 模型上。
  3. 实测里最大赢家是中等模型（如 Qwen3-8B），这对国产模型生态是直接利好。
  4. "让模型自己写代码读上下文" 这件事已经从 Demo 走到 SOTA 工程模板，团队现在就该评估接入成本。
  5. 先复制、再优化、最后超越：官方 lib + DSPy 已给出最低门槛，不必从零造。
