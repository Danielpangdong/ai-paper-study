01 · 标题与知识地图位置

资源指示器（Resource Indicators）

专业定义 OAuth 2.0 的 resource 请求参数。客户端可在授权请求或令牌请求中，用一个绝对 URI 标识它希望把即将取得的访问令牌用于哪个受保护资源；该标识可帮助授权服务器决定令牌内容、加密方式与受众限制。

白话解释 你不是只说“我需要读数据”，而是说“我需要读 https://calendar.example.com/ 的数据”。前者像申请“阅读权限”，后者还把要进的楼栋写清楚。

与前一课的连接：受保护资源元数据（RFC 9728）告诉 AI 客户端“这个 API 是谁、认可哪家授权服务器”；资源指示器则把这个已识别的 API 放进申请，要求一张只给它使用的令牌。前置：Access Token、OAuth Scope、受保护资源元数据。后续候选：JWT 的 aud 校验、Rich Authorization Requests、OAuth Client ID Metadata。
02 · 为什么重要

“有读权限”仍然不够：系统还得知道令牌要在哪里兑现

问题

Scope 主要回答“做什么”

files.read、calendar.read 这类 scope 描述动作或能力；在多 API 环境里，它不必然指出令牌应交给哪一个 API。

后果

广泛可用的 Bearer Token 更怕被转交

拿到 bearer token 的一方若能把它交给别的资源服务器，泄露或钓鱼得到的令牌就可能被“换一扇门”滥用。

资源指示器补上的不是“更多权限”，而是“更窄的兑现地点”。

没有它会怎样？在一个授权服务器服务许多 API 的部署中，客户端只能靠约定或私有参数猜令牌目标；令牌更难按资源定制，资源服务器也更难坚定地拒绝“不属于我”的令牌。RFC 9700 建议访问令牌应限制到一个资源服务器（或很小的一组），且资源服务器对每次请求都要核对。

05 · 工作原理

从“我要访问这里”到“这里只认自己的令牌”

  1. 识别目标资源。客户端先确定真正要调用的 API 基 URI。若是动态发现的 API，可先读取受保护资源元数据；不是把授权服务器 URL 当成资源。
  2. 在请求中给出 resource。它的值必须是绝对 URI，不能带 fragment；客户端应尽量给出能覆盖所需 API 的具体 URI。它可出现在授权请求和/或令牌请求中。
  3. 授权服务器套用策略。服务器把“请求者、用户授权、scope、resource”一起判断，决定是否签发、给哪个资源定制何种令牌；请求不等于自动批准。
  4. 令牌带上（或关联）目标受众。对于遵循 RFC 9068 的 JWT access token，若请求给出了 resource，对应 aud 应为同一值；不透明令牌也可以在服务端保存这种关联。
  5. 目标 API 逐次验证。它验证发行者、签名和有效期，再确认 aud 里有自己预期的资源标识，并检查当前动作所需的 scope/权限；不匹配就拒绝。

教学提醒：RFC 8707 允许多个 resource 参数，但 RFC 9700 倾向让访问令牌只面向单个（或很小集合）资源。多受众令牌容易让 scope 与资源的对应关系含混，应有明确的服务端策略。

06 · 关键术语

把四个相邻概念分开，脑中的地图才不会串线

resource 参数

专业解释RFC 8707 定义的 OAuth 请求参数：受保护资源的绝对 URI 标识。
白话解释申请时写明“我要把令牌交给哪家 API”。
易混淆点它不是 API 调用 URL 的每个路径和查询串，也不是授权服务器的 issuer。

受众限制（Audience Restriction）与 aud

专业解释令牌只可被指定资源服务器接受；JWT 常以 aud claim 承载。
白话解释钥匙背面刻着“只开 B 楼”。
易混淆点aud 是验证时检查的属性；资源指示器是申请时的输入。二者相关，不能机械等同。

Scope（授权范围）

专业解释OAuth 表达请求访问范围的字符串集合；资源服务器按其语义授权动作。
白话解释证上写“可阅读、不可修改”。
易混淆点scope 有时被私有约定拿来指资源，但其首要问题是“做什么”，不是“交给谁”。

受保护资源（Resource Server / API）

专业解释接收令牌并提供受保护数据或能力的服务。
白话解释真正检查证件、打开门的楼栋。
易混淆点它不是授权服务器；前者验证并执行请求，后者颁发/管理授权。
07 · 真实应用

MCP 授权：AI 客户端不能把 A 工具的令牌带去 B 工具

事实 Model Context Protocol 的 2025-06-18 Authorization 规范要求 MCP 客户端实现 RFC 8707：在授权请求与令牌请求中包含 resource，并用 MCP server 的规范 URI 标识目标。规范还要求 MCP server 验证令牌是专门为自己签发的，禁止接收或转发其他令牌。

推断 对能自动挑选工具的 AI agent，这种目标绑定尤其有价值：工具目录、重定向或恶意服务若试图诱导它为错误目标取令牌，严格的资源 URI 与受众核验能缩小令牌被“转门使用”的空间。它仍需要可信的元数据发现、TLS、发行者校验与最小权限共同配合。

09 · 常见误区

四个看似合理、其实会放大边界的说法

×
“有 files.read 就能读所有文件 API。”
不对。scope 是否可用必须与目标资源共同解释；受众不匹配的令牌应被当前 API 拒绝。
×
“resource 就是请求要访问的完整 URL。”
不必然。它是资源标识，通常是 API 基 URI；RFC 8707 建议客户端提供覆盖所需 API 的最具体 URI，而不是把每次调用的动态 query 拼进去。
×
“客户端写了 resource，授权服务器就必须签发。”
不对。它只是请求输入。授权服务器仍要验证客户端、用户授权、资源策略并可拒绝未知或不允许的目标。
×
“只要 JWT 有 aud 就安全了。”
不对。资源服务器还要验类型、签名、发行者、到期时间、受众与实际权限；受众限制不能替代防盗、撤销或发送者约束。
10 · 限制、风险和适用边界

它缩小“令牌能去哪”，却不独自解决“谁可信、谁被盗”

URI 是安全边界

资源 URI 选择过宽会扩大可用范围；多租户场景若租户标识在路径中，可能需要更具体的资源标识。不同规范的规范化规则也须一致。

受众校验必须落地

只签发带 aud 的 JWT 却让 API 不检查，等于没装门禁。令牌是 opaque 时，也要由内省或服务端数据实施等价校验。

泄露仍是风险

目标绑定降低跨资源转用的影响，不会阻止攻击者在正确目标处使用被盗 bearer token；需结合短时效、DPoP/mTLS、撤销与安全客户端。

适用：一个授权服务器面对多个独立 API、AI agent 调多个工具/MCP server、令牌需要按资源定制或有跨资源钓鱼风险。不应夸大：它不是所有 OAuth 部署的强制万能开关；采用时要让客户端、授权服务器、资源服务器对 URI 和校验语义达成一致。

11 · 三句话总结与自测

把这三句话带走

  1. 资源指示器让客户端在申请令牌时说明目标受保护资源，而 scope 主要说明想做的动作。
  2. 授权服务器可以据此签发面向该资源的令牌；资源服务器必须验证令牌的受众与自身相符。
  3. 它是 AI 工具调用的“目标锁”，要与可信发现、最小权限、令牌验证和发送者约束一起使用。
题 1：为什么 scope=read 不能单独回答“这张令牌能交给哪个 API”？
答案：scope 表示动作范围，不天然表达资源身份；多个 API 可能都有 “read”。需要 resource/audience 把动作和兑现地点一起约束。
题 2：resource 和 JWT 的 aud 是不是同一个东西？
答案：不是。前者是请求时的目标声明；后者是令牌中的受众约束（对 RFC 9068 JWT，使用 resource 时应对应同一值）。二者构成申请到验证的链路。
题 3：Finance API 收到一个签名有效、scope 足够但 aud=HR API 的令牌，应怎样做？
答案：拒绝。资源服务器应确认令牌是为自己签发；签名和 scope 有效并不让它成为 Finance 的令牌。
