01 · 为什么这个概念重要

让短期通行证到期，而不是让用户每天重新登录

AI 日历助手若每天早上都要汇总行程，不能要求用户每天重新打开授权页，也不该永久
持有一张能直接读数据的通行证。刷新令牌把这两个问题拆开：短命的 Access Token 用
来访问 API；更受保护的 Refresh Token 只负责向授权服务器换取下一张短命令牌。
它解决什么

离线、长期但可控的连续服务

用户不在场时，应用仍能在已获授权的范围
内续领短期令牌，例如定时整理日程或做文
件备份。
事实 · 协议的分工

没有它会怎样

便利与最小暴露之间难两全

要么频繁打断用户重新授权，要么把直接访
问 API 的令牌做得很长寿，后者会让泄露
后的可利用时间更长。

RFC 6749 将 Refresh Token 定义为“取得 Access Token 的凭证”：当前 Access Token 失效或
到期时，客户端拿它向授权服务器领取新的 Access Token；它只应发送给授权服务器，不应发
送给资源服务器/API。

用户首次同意最小权限。客户端请求特定 scope；授权服务器决定是否同意，以及是否为该
客户端签发 Refresh Token。签发并非必然，取决于风险和产品策略。
客户端收到两种不同用途的凭据。Access Token 用于调用 API；Refresh Token 被保存为更
敏感的长期秘密。两者不应互换用途。
客户端用短期 Access Token 调用 API。资源服务器核验它的时效、受众、范围与自身业务
策略，允许或拒绝访问。
短期令牌到期或失效。客户端应处理 API 的失败响应，而不是假设一次授权会永久成功。它
也可以在到期前按授权服务器规则尝试刷新。
客户端把 Refresh Token 交给授权服务器。授权服务器检查它是否仍有效、是否属于这个
客户端、是否已撤销，以及请求的范围是否允许。

授权服务器发新令牌或拒绝。通过时返回新 Access Token，并可能轮换出新的 Refresh
Token、使旧的那个失效；失败时应用应要求重新授权，而不是静默扩大权限。

推断 · 对 AI Agent 的意义
长时间运行的 Agent 更需要把“理解任务”和“保存高价值秘密”拆开。模型可提出“需要续期”，
但实际刷新、秘密存储、撤销与异常处理应由受控的应用服务完成。

06 · 一个真实应用案例

每早自动整理日程的日历助手

假设用户允许一个日历助手在每天早上生成“今天的会议准备清单”。第一次连接时，应用把用户带
到授权页面，请求读取日历所需的 scope；在服务商允许离线访问、且用户同意时，应用可获

Refresh Token。第二天，短期 Access Token 已到期，应用把 Refresh Token 交回授权服务器换取
新的短期令牌，再读取日程。
真实机制

产品边界

Google 的离线授权

Google 的 OAuth 官方指南说明：应用若请
求 offline 访问，在授权码交换后可获得
Refresh Token；之后即使用户不在场，也
能用它取得新 Access Token。它也提醒应
用安全、长期保存令牌。

“自动读取”不等于“自动修改”

读取日程做摘要与替用户删除会议是不同风
险。写入、删除、发送邀请等高影响动作仍
应采用最小权限、预览确认、审计和撤销。

长。

08 · 常见误区

四个很容易犯、却会带来安全后果的错误
常见说法：“Refresh Token 就是寿命更长的
Access Token。”

实际情况：它们的接收方不同。Refresh Token 只拿给授权
服务器换新令牌；Access Token 才被 API 用来判断本次访
问。

为什么：把高价值续证凭据带到更多地方，会扩大泄露面。

常见说法：“有了 Refresh Token，应用永远不 实际情况：授权服务器可以不签发、让它过期、撤销，或
需要再问用户。”
因风险/策略拒绝刷新。应用必须准备重新授权的路径。
为什么：“方便”是授权服务器在当前条件下给出的能力，不是永久承诺。

常见说法：“令牌轮换就不会泄露。”

实际情况：轮换主要用来缩短旧令牌的可用窗口、帮助检
测重复使用；秘密仍需要安全存储和传输。

为什么：攻击者若在正确时间使用被盗令牌，仍可能造成损害。

常见说法：“AI 能刷新令牌，就能自动做任何 实际情况：刷新只解决“如何重新拿到既有授权范围内的短
事。”
期令牌”；高影响动作还要受 scope、资源策略和用户确认
约束。
为什么：令牌管理是权限基础设施，不是业务决策替代品。

09 · 现实限制与风险

它把风险集中起来，所以更要谨慎设计
长期秘密更值得被攻击

Refresh Token 往往能不断换取新的 Access Token。RFC 9700 指出，它们对攻击者很有吸引
力；一旦被窃取并重放，攻击者可能代表用户铸造新的 Access Token。因此必须在存储和传输中
保密，并经 TLS 传递。

公共客户端的保存条件更苛刻

浏览器或移动端并不总能安全保存长期秘密。RFC 9700 要求公共客户端的 Refresh Token 采用
“绑定发送者”或“令牌轮换”之一来防范重放；实际可用能力仍取决于授权服务器。

轮换会带来状态与并发问题

每次刷新都换新令牌，应用必须原子地保存最新令牌。如果两个任务同时拿旧令牌刷新，其中一
个可能被判为重放；这是安全信号，也要求产品有可靠的错误恢复和重新授权提示。

技术令牌不能替代用户意图

令牌允许调用 API，不代表每一次自动化动作都符合用户当下意图。涉及发信、删除、支付、对
外发布时，应叠加显式确认、额度、审批、日志与撤销。

检查你是否真的掌握了
1. 一句话题

为什么 Refresh Token 不该直接发送给日历 API？
参考：它的用途是向授权服务器换取新的 Access Token；日历 API 是资源服务器，应只接收用于本次访问
的 Access Token。把 Refresh Token 送到更多地方会扩大长期秘密的泄露面。

2. 区分题

Access Token、Refresh Token、ID Token 分别最应该交给谁？
参考：Access Token 给资源服务器/API；Refresh Token 给授权服务器；ID Token 给客户端应用以处理登录
身份信息。

3. 迁移题

一个 AI 助手每小时读取一次文件摘要。它把 Refresh Token 写进浏览器控制台日志，并让所有
并发任务同时刷新。你会建议哪些改变？
参考：把令牌移到受保护的秘密存储，禁止日志输出；使用 TLS 与最小 scope；让刷新操作串行化/原子保
存最新令牌；处理轮换导致的失效并提供重新授权和撤销路径。
