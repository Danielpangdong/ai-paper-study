OAuth 受保护资源元数据

OAuth 2.0 Protected Resource Metadata · RFC 9728

让一个 AI 客户端先问清楚：“这个 API 接受谁签发的令牌、要什么权限、令牌该怎样交？”再去申请正确的通行证。

01 · 为什么重要

授权服务器的“能力目录”不等于资源 API 的“入场说明”

上一课的 mTLS 解决“偷到令牌还够不够”的问题；今天解决更早的一步：AI 已经找到一个受保护 API 后，到底该向哪个身份系统申请、为这个 API 使用的令牌？

没有它会怎样？

客户端只能把授权服务器地址写死，或猜测配置。服务迁移、一个域名下有多个 API、不同租户各用不同身份系统时，猜测容易把用户带到错误登录页，或为错误目标申请令牌。

它提供什么？

事实：RFC 9728 定义 JSON 元数据，使 OAuth 客户端与授权服务器获得同受保护资源交互所需的信息；资源可声明其标识、关联授权服务器、支持的 scopes 与令牌呈现方式等。

一句人话：受保护资源元数据就像 API 自己贴在门口的“取件说明卡”：不是通行证，也不替你验证身份；它告诉客户端该去哪个窗口办哪一类通行证。

02 · 贯穿类比

把它想成“智能取件柜门上的取件说明”

你（AI 客户端）来到一排智能柜（受保护资源）。柜门不会因为你说“我是来取件的”就打开，而是先给你一张说明：哪家身份核验台发的取件码才有效、可取哪类格口、需要怎样出示码。你带着这张说明去身份核验台（授权服务器）申请取件码（Access Token），再带回同一个柜门。

类比边界：真实协议不是“柜门相信一张纸”。客户端必须核对元数据中的 resource 是否与自己要访问的资源完全一致，并依赖 HTTPS；签名元数据还有额外的签发者验证。说明卡本身不认证用户、不发令牌，也不会自动让资源接受令牌。

04 · 工作原理

从“我想调用它”到“我带着给它的令牌回来”

  1. 确定资源标识。客户端知道要访问的 HTTPS 资源 URL，例如某个 MCP 服务端点；它不是先从 Scope 猜资源。
  2. 发现元数据地址。资源可在未携带有效令牌时返回 401 与 WWW-Authenticate: Bearer resource_metadata="…"；客户端也可按 RFC 9728 的确定规则构造 well-known URL。
  3. GET 一份 JSON “自我说明”。典型内容包含 resource、authorization_servers、scopes_supported、令牌呈现方式，以及 DPoP/mTLS 等能力声明。
  4. 先验证，再使用。返回的 resource 必须和目标资源标识完全一致；否则元数据不能使用。客户端还须采用 HTTPS，并谨慎处理接下来将要请求的授权服务器地址。
  5. 继续发现授权服务器。用资源元数据给出的授权服务器标识，读取上一课讲的授权服务器元数据，找到授权端点、令牌端点、PKCE 支持等。
  6. 申请面向该资源的最小令牌。在支持的情况下，客户端用 RFC 8707 的 resource 参数明确目标；Scope 表示“能做什么”，资源标识表示“在哪儿使用”。
  7. 带令牌回到资源服务器。资源仍须检查令牌有效性、受众是否是自己，并在需要时验证 DPoP 或 mTLS 绑定。元数据没有替资源做这些检查。

05 · 关键术语

每个词都放在正确的位置

受保护资源
Protected Resource / Resource Server
专业解释：需要 OAuth 访问令牌才能提供数据或能力的 API/服务。白话：真正那扇要打开的柜门。
易混淆：它不是授权服务器；它通常不负责让用户登录或签发令牌。
资源元数据
Protected Resource Metadata
专业解释：资源发布的 JSON 配置，声明资源的身份、OAuth 交互所需能力与关联。白话：柜门的取件说明。
易混淆：不是 Access Token，也不是用户资料。
授权服务器
Authorization Server
专业解释：执行授权交互并签发访问令牌的 OAuth 角色。白话：身份核验台。
易混淆：授权服务器元数据描述的是“核验台有哪些窗口”；资源元数据描述的是“柜门认可哪些核验台”。
资源指示符
Resource Indicator
专业解释：RFC 8707 的 resource 参数，用于明确令牌打算在哪个资源使用。白话：在办码申请上写“这张码只给 3 号柜”。
易混淆：Scope 是“可做什么”，resource 是“去哪里用”。
Token Audience
令牌受众
专业解释：令牌被设计给哪些接收方使用的约束，JWT 常用 aud 表达。白话：票上写的指定场馆。
易混淆：元数据会帮助客户端找到正确资源/发证者，但受众校验发生在资源服务器接收令牌时。

06 · 有来源的真实应用

MCP 的授权发现：让 AI 客户端不必硬编码身份系统

事实（MCP 2025-11-25 规范）：受保护 MCP 服务器必须实现 RFC 9728，MCP 客户端必须用它发现授权服务器。服务器可在 401 的 WWW-Authenticate 中给出 resource_metadata，或在 well-known URL 发布元数据；客户端应优先使用响应头给出的地址，缺失时再按规定构造 URL。

推断（基于规范的工程含义）：当一个 AI 工具客户端接入多个第三方 MCP 服务时，它可以把“哪个授权服务器为哪个服务发证”的关系从手工配置，转为每个资源可验证的自描述发现。这降低接入耦合，但不消除信任、注册、同意与令牌验证的工作。

一个具体链路：AI 客户端请求 https://mcp.example.com/public/mcp → 收到 401 与 metadata 指针 → 读取其中的授权服务器标识与 scope 提示 → 发现该授权服务器的端点与 PKCE 能力 → 申请带该资源标识的令牌 → 回到同一 MCP 服务。MCP 还要求服务仅接受明确发给自己的令牌，不得把收到的令牌透传给上游 API。

08 · 三个常见误区

别让“自动发现”变成“自动相信”

误区 1：有了元数据，客户端就能盲信任何登录页。
纠正：元数据中的 resource 必须与目标资源完全匹配；HTTPS、签名验证（如使用）与防钓鱼 UI 仍是安全边界。
误区 2：scopes_supported 列出的权限都该申请。
纠正：RFC 9728 明确它只是资源愿意公开的支持列表；客户端仍应为当前操作请求尽可能小的权限集。
误区 3：资源元数据已经验证了令牌。
纠正：它只告诉客户端可能的要求和关系。资源服务器在收到令牌后仍要验证有效性、受众、Scope，以及 DPoP/mTLS 等约束。
误区 4：Scope 就等于目标 API。
纠正：Scope 常表示动作或权限；RFC 8707 的 resource 参数专门表达“这张令牌要在哪个资源使用”。

09 · 限制、风险与适用边界

它把配置变成可发现，不把信任变成免费

适合

AI 客户端会接入多个独立 API/MCP 服务；资源与授权服务器可分离；需要降低硬编码配置、支持服务迁移，或让客户端根据资源声明协商 DPoP/mTLS 等能力。

未必需要

完全封闭、授权服务器与资源关系永久固定且由同一应用静态配置的系统。即便如此，静态配置也需要安全发布与变更管理。

风险 1：SSRF。客户端会根据元数据里的授权服务器标识继续发请求；RFC 9728 专门指出恶意资源可能诱导客户端访问内网地址。实现应限制内部 IP 段、重定向与请求目标。
风险 2：钓鱼与错误信任。用户选择或资源被攻陷时，攻击者可能把授权引导到恶意站点；客户端应清晰展示授权服务器域名，不能把元数据当成信任锚。
风险 3：陈旧缓存。普通 HTTP 缓存行为适用；服务更新关联授权服务器时，要设计 Cache-Control、刷新与失败恢复策略。

10 · 带走三句话

把今天的概念装进脑中

  1. 受保护资源元数据是资源 API 的 OAuth 自我说明：告诉客户端该怎么与它安全协作。
  2. 它先把客户端从资源带到正确的授权服务器；之后仍要走授权、取令牌与资源端验证。
  3. 它与 Scope、资源指示符、授权服务器元数据、令牌内省各管一段，合起来才形成完整的 AI 工具授权链。

三道理解题

1. 一句话说清今天的概念？
资源 API 发布的一份可验证说明，帮助客户端找到合适的授权服务器并了解访问要求。
2. 输入 → 步骤 → 输出是什么？
输入是资源 URL/401 挑战；步骤是取回并验证元数据、发现授权服务器、申请面向该资源的令牌；输出是资源可验证并接受的最小权限令牌。
3. 它和授权服务器元数据最大区别？
前者由资源发布、说明“谁可访问我”；后者由授权服务器发布、说明“如何向我申请令牌”。

11 · 知识地图增量

今天把“资源端”接回此前的授权链

继承：Access Token、Scopes、PKCE、DPoP、mTLS、Token Introspection、授权服务器元数据。
今日新增：从资源端发现授权服务器的标准入口；resource_metadata、well-known URL、resource 一致性校验。
被修正：“知道授权服务器地址”不是万能前提；在动态多资源场景，资源可声明自己认可的授权服务器，但这不是无条件信任。
下一步候选：① Token Audience 与 RFC 8707 Resource Indicators；② Rich Authorization Requests（把“能做什么”细到具体对象）；③ OAuth Client ID Metadata（陌生客户端如何被识别）。

12 · 来源账本

可回溯的一手资料

[S1] IETF RFC 9728（2025） — 定义、well-known 路径、JSON 响应、resource 精确匹配、401 resource_metadata、TLS/SSRF/缓存边界。
https://datatracker.ietf.org/doc/html/rfc9728
[S2] IETF RFC 8707（2020） — resource 参数表达令牌使用目标，并支持更严格的 audience 限制；与 Scope 的职责不同。
https://www.rfc-editor.org/rfc/rfc8707.html
[S3] Model Context Protocol Authorization Specification（2025-11-25） — MCP 服务器必须实现 RFC 9728、客户端必须使用其发现授权服务器；给出 401 头与 well-known 的发现顺序，并要求资源校验 token audience。
https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization
证据标签：事实为上述规范明确规定；类比只用于理解；推断是基于规范的工程含义，不是规范承诺的业务结果。
