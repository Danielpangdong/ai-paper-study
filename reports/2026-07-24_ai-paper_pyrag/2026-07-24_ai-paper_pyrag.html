我们的选择 相对 6 月 27 日的上下文工程，今日新增是把跨步依赖做成可执行接口；相对近期 Agent PR/RHO，研究对象是证据链，不是代码协作或机器人策略。

一句话讲透

普通 RAG 像一次性把问题丢进搜索框；PyRAG 像先写一张可运行的办事清单：每一步取什么资料、答案存哪个变量、下一步引用哪个变量。程序报错时得到解释器错误，不是模型对自己的“感觉”。

问题背景

多跳问题先得 A，再用 A 查或比较 B。自由文本轨迹会让检索词漂移、变量依赖隐形，也让模型用自己的文字判断自己是否走错。作者声称 单跳事实问答中 vanilla RAG 已是强基线；优势主要在组合式多跳数据集。

核心贡献

  1. 将多跳 RAG 改写为 retrieve(query,topk) 和 answer(query,docs) 的 Python 程序合成与执行。
  2. 拆出 Decompose、Plan、Answer；中间答案存变量，形成依赖图与执行日志。
  3. 异常触发修计划；证据不足只扩展该步 top-k，无需额外训练。
  4. 同设置/切分比较 Direct、CoT、Vanilla RAG、Self-Ask、IRCoT、ITER-RETGEN。

技术路线

工作原理与类比边界

类比：旅行报销单把机票、酒店、汇率列成字段，公式再引用字段；不会把它们藏在一段随笔里。边界：程序能运行只证明语法、变量与类型，不证明检索网页可信或 Answer Agent 抽对答案。我们的推断 应把失败可诊断性当产品指标，不能把 Python 化当事实验证或安全沙箱。

失败案例与局限

论文数据支持 Figure 4b/4c 将约 95% 失败归到 Answer Agent，程序错误约 5%；§A 指出 sentinel 字符串可能被插入后续查询，且“只检索一次”的欠分解不会触发编译错误。

安全边界：README 以 exec() 执行模型生成 Python。研究原型不可原样生产化；应限制内建能力、隔离进程、设资源上限、收窄工具面。

可复现性

已核验 作者 GitHub 有代码、requirements、训练/评测入口、模型和数据链接；训练免费版需要 vLLM 与检索服务，RL 建议 1 节点 8×A100 80GB。交叉核验 HotpotQA 官方仓库有基线、下载、预处理、训练和评测 pipeline（Apache-2.0），支持基准基础设施可检查，但不是 PyRAG 的独立复现。PyRAG 页面未见明确 LICENSE 文件，不作许可证断言。

产业影响

我们的推断 高价值、可拆分、需审计的客服升级、合规检索、研究助理和故障排查，可从“最终答案黑盒”转为带依赖图的证据工作流。

产品/创业/投资启示与失效条件

可验证假设：2–4 个可独立查子问题时，“可执行依赖图 + 节点级复核”在相同正确率门槛下可减少人工复核范围。应 A/B 任务准确率、人工分钟数、P95 延迟、每成功任务成本。失效条件：单跳、工具不可控、来源噪声大、不能原子化、或无法隔离执行时，额外开销可能不值。

三句话复盘与 3 道理解题

① 核心是显式变量与可执行计划，不是“多几个 Agent”。② Table 2 是作者组合式基准结果，不是生产承诺。③ 解释器能修程序，不能保证证据正确。

问 1：为何易排错？——中间值、依赖与异常可定位。
问 2：+25.5 点不能说明什么？——不能说明所有知识问答同样提升。
问 3：上线先补什么？——受限隔离执行与工具权限，随后结构化证据信号。

跨期研究增量

继承：上下文工程重视给模型恰当信息；Agent 长链增加失败点。新增：把“查什么、得到什么、下一步依赖什么”改成程序数据流。修正：可执行不等于事实可验证，主要失败仍在检索/Answer 层。下一问：真实企业数据中，trace 能否提高人工复核效率、降低成功任务成本？
