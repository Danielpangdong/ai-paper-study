科研 Agent 的成绩单，为什么不能只看“会不会做题”

《SciAgentArena》把近 200 个真实科研工作流拆成可验的中间步骤。结论很克制：今天的 Agent 已能替人完成一部分边界清楚、答案可核的分析；但离“自主科学家”还差着方法选择、稳定性与先验证再行动这三道门。

arXiv:2606.127362026-06-10预印本 · living benchmark
一句话讲透：把 Agent 放进真实科研流程后，最值得自动化的不是“灵感”，而是带输入契约、过程检查与人工签字的固定分析段。

问题背景

传统榜单常把“最后答对了吗”当作唯一分数。可是在科研里，结果对并不表示过程可靠：一段代码可能能跑，却用了错误的包函数；一条结论可能看似合理，却来自单位混杂的数据。作者因此把任务分成四类：数据分析、优化、发现、有效性验证，并要求输出经过独立评测环境检查。

作者声称：这套分离运行框架与评测框架的设计，可处理不同 Agent 的环境冲突，并让稳定性、可靠性、成本与最终正确性一起进入评价（论文 §2.1、图 1d）。

核心贡献

  1. 问题像科研，不像问答：任务覆盖从分子到患者的五个层级，而不是只问一个知识题。
  2. 过程可验：把输出代码/数据交给统一评测端，检查每一步是否符合预期。
  3. 比较多个 Agent：论文覆盖 18 个 Agent，故能观察“谁在哪类任务上强”，而非宣布单一总冠军。
  4. 把失败当数据：归纳 API 幻觉、默认方法收敛、无效前提照做等可工程化修补点。

工作原理与类比边界

类比：把它想成驾校路考，而不是刷选择题。车能发动（代码运行）不等于会安全变道（中间步骤正确），更不等于会在“前方无路”的指令前停车核验（有效性验证）。

类比的边界：科研没有一份全知的“标准路线”。基准能严查已定义的步骤与输出，却不能证明一个 Agent 的新假说必然有科学价值；因此“发现”分数尤其不应被当作自动化发现的生产保证。

关键实验解读

图 2｜最强 Agent 仍留下的“真科研”缺口

来源：论文图 1e；hERG=药物发现 AUROC，DEG=差异表达 F1，SVG=空间变异基因 Jaccard。图中是每项的最佳 Agent，不是同一个 Agent 的总成绩。读图结论：数学题 100 分不能外推为现实科研工作流已解决。

论文数据支持：单祖源 PRS 任务中，Claude Code 与 STELLA(mem) 通过全部 14 个子步骤；多祖源 PRS 中，GPT‑5.2 为 14/18，AutoBA 为 8/18（论文 §2.4）。这说明“多一步跨祖源整合”足以改变可靠性排序，不能只看单点成功。
论文数据支持：空间组学错误分析中，48.6% 的错误属于“调用不存在的代码”，运行错误和选错函数各占 22.9%（论文 Supplementary Fig. 8b 的文字解读）。这不是模型“不会写 Python”的简单同义词，而是专用科学 API grounding 的问题。

可复现性

代码仓库公开了 Agent 配置、评测目录及前端；README 写明单次提交上限 2 GB、执行超时 15 分钟。数据集页列出跨域、药物、EHR、遗传、单细胞与空间组学的数据结构，但访问前需同意条件，单细胞数据约 12 GB、空间组学约 4 GB。可复验并不等于一键复现：请记录 commit hash、依赖版本、模型版本、提示词、随机种子、成本上限与失败重跑策略。

独立交叉核验：尚未发现第三方对 SciAgentArena 全量复跑的公开结果（该工作很新）。因此本文没有把项目自带 leaderboard 当作独立复现。作为评价设计的外部基线，ICLR 2024 的 AgentBench 也以 8 个交互环境衡量 Agent；τ-bench 则用终态数据库与 pass^k 检查多次运行可靠性，报告 GPT‑4o 成功率低于 50%、零售域 pass^8 低于 25%。两者支持“交互与一致性必须单列评测”的方向，但不验证 SciAgentArena 的具体分数。

产业影响

近期可用：标准化的生信清洗、固定结构的 FHIR 检索、明确 schema 的化学数据处理——前提是有测试、版本固定和专家复核。不应承诺：自主提出药物机制、替代临床/科研负责人、在未知 API 和脏数据上稳定工作。

我们的推断：科学软件公司真正的护城河更可能是“任务契约 + 可验中间产物 + 版本化工具目录 + 审批痕迹”，而不是一个声称无所不知的聊天界面。这是由论文观察推导出的产品判断，非作者直接实验结论。

三句话复盘与 3 道理解题

  1. SciAgentArena 的关键不是多一个总分，而是把真实科研任务拆成可验证过程。
  2. 最强 Agent 在代表性任务上仍常低于 70，且空间组学错误中 48.6% 是不存在的代码。
  3. 正确的商业落点是“有闸门的固定流程自动化”，不是跳过验证的自主发现承诺。
1. 为什么“代码能运行”仍不足以证明科研 Agent 可靠？
2. 若把一个 PRS 流程从单祖源扩展到多祖源，哪类中间检查最值得新增？
3. 你会用哪一个过程指标，来约束一个宣称能做科学分析的产品？为什么？

跨期研究增量

继承结论：前期的 Agent 论文已提示，记忆、并发与奖励机制都会使“看起来完成任务”不等于可靠完成。今日新增：SciAgentArena 将这件事落在跨科学域的执行工作流，并量化了任务层级、专用工具 API 与重复运行带来的断裂。被修正/证伪：“只要通用模型更强，就自然能成为更可靠的科学 Agent”不被本文支持——没有任何单一 Agent 跨任务统治，专用能力与工程契约都重要。下一验证问题：在盲测的新任务、固定成本和相同工具条件下，加入 API 自检与 premise check 能否同时提高通过率和稳定性？
