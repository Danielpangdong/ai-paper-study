OAuth 授权范围
OAUTH SCOPES

登录不是万能钥匙：如何让 AI 只拿到完成一件事所需的那几把钥匙？

行指定动作。

01

为什么这个概念重要？

AI 助手一旦接上邮箱、日历、网盘或企业系统，“会回答”就变成“会行动”。问题不再只是它会不会理解你，而是：
它能碰哪些数据，能按下哪些按钮？
它解决的问题

把“登录成功”拆成具体权限

OAuth 的 scope（授权范围）让应用在请求访问时说清楚
边界，例如“只读日历”或“发送一封邮件”。资源服务器据此
拒绝清单外的请求。

没有它会怎样

一把钥匙打开太多门

如果一个日历提醒功能一上来就申请完整邮箱、联系人和云
盘权限，用户既难判断风险，令牌泄露时的损失也会被放
大。

事实：RFC 6749 把 scope 定义为由授权服务器解释的一组、以空格分隔的大小写敏感字符串；每个字符串增加一段访问范
围。服务器可只批准其中一部分，并应告知客户端实际批准了什么。
这正是昨天“最小权限”原则的工程化版本：最小权限是设计原则；scope 是常见的、对外可展示的授权表达。

关键术语：一张申请单里的各个角色

授权范围
scope

专业：授权请求和令牌响应中的一组范围字符串，用于表达访问请求/授予的范围；具体
语义由授权服务器定义。
白话：值班证上写的“只进 A 区、只查看、不许修改”。

易混淆：scope 不是全球统一的权限词典；同样叫 read 的词，在两家服务里可能含义
不同。
访问令牌
access token

授权服务器
authorization server

专业：客户端带给资源服务器的凭证，用来代表一次已完成的授权，并在请求中通常放
在 Authorization 头部。
白话：能让门禁核验的电子值班证；scope 是证上写的可做事项之一。
易混淆：令牌不等于密码，也不等于用户本人；它可能过期、被撤销或只对特定服务有
效。

专业：认证资源所有者、收集同意并签发令牌的系统。
白话：发证处：你在这里确认，而不是把账号密码告诉每个应用。
易混淆：它与存放数据的资源服务器可以是不同系统。

资源服务器
resource server

专业：实际托管受保护 API 或数据，并验证令牌后决定是否响应的系统。
白话：真正的门禁：日历、邮箱或网盘服务本身。

易混淆：它不能只看“令牌长得像真的”，还要检查它是否为自己签发、是否尚有效、范
围是否足够。
增量授权
incremental authorization

06

专业：在用户需要某功能时，再申请那项功能所需的额外范围，而非初次登录时一次索
要全部。
白话：先借会议室钥匙；你真的要寄快递时，再问能否借储物柜钥匙。
易混淆：这不表示可以反复骚扰用户；每次升级都应有明确任务、清晰说明和可预期的
失败处理。

真实应用案例：日历助手为什么不该先要邮箱？

以 Google 的 OAuth 文档所示的日历场景为例：应用在用户真正点击“添加到日历”时，再请求日历访问，而不是在
一开始就申请。Google 也要求应用核对用户实际批准的范围，并针对未获批范围关闭相应功能。

任务 A：找出空闲时间

合理申请：日历只读范围。
合理结果：助手可读取必要的日历信息来建议时间；它不应
因此自动查看联系人或删除邮件。

任务 B：用户点“创建会议”

升级时机：用户明确表达创建活动的意图。
合理申请：此时才请求创建日历活动所需范围；若用户拒
绝，应用仍可保留“只读建议”的功能。

可迁移的产品规则：把 scope 请求绑到用户可见的动作；用人话说明“为什么需要”；把“部分同意”当成正常分支，而不是异
常。

09

现实限制与风险：Scope 不是安全魔法

把范围做小很重要，但它无法单独处理所有风险。好的系统会把范围、时效、受众、交互确认、审计和撤销组合起
来。

范围太宽

“全盘访问”方便开发，却提高误
操作与令牌泄露的影响面。优先
用最具体、非敏感且能完成任务
的范围。

令牌被盗或被误送

scope 再小，令牌泄露后仍可能
被滥用。应缩短有效期、避免把
令牌放进 URL，并使用受众限制
等机制。

AI 的意图被操纵

提示注入可能诱导 AI 尝试不相关
的工具调用。scope 可让越权调
用被拒绝，但高风险写操作仍宜
加确认和日志。

实践清单：① 先写清任务 → ② 选择最小范围 → ③ 在真正需要时再升级 → ④ 以实际获批范围更新界面 → ⑤ 给写操作加确认
与审计 → ⑥ 支持撤销与失效处理。

三句话总结

1. Scope 是边界清单

它告诉系统：这张访问令牌可覆盖哪
些资源/动作范围；具体语义由服务
提供方定义。
11

2. 最小与按需更安全

不要因为“以后可能用到”就全要；让
用户在明确任务发生时，才批准新增
范围。

三道理解题：能把边界讲清吗？

3. Scope 不是唯一门禁

资源服务器还应检查令牌有效性、受
众、用户原有权限、资源归属和组织
策略。

题 1｜一句话
如果朋友问“OAuth scope 是什么”，你会怎么说？

参考答案：它是授权时写明“这个应用的令牌能做什么”的清单，例如只读日历、不能删除邮件。
题 2｜判断
某应用申请了 calendar.read，它是否必然能读取公司所有同事的日历？

参考答案：不必然。scope 之外，日历服务还会检查用户对具体日历的权限、组织规则、令牌有效期与资源
归属。
题 3｜迁移题
你在设计一个“帮我整理差旅”的 AI。它刚开始只需读日历，用户后来点击“代我发送确认邮件”。你会怎样设计 scope 请求？

参考答案：初始只申请完成行程建议所需的日历只读范围；在用户点击发送前，用人话说明用途并单独申请
发送邮件所需范围。若拒绝，保留行程建议、关闭代发功能；对发送再加最终确认与日志。

来源与说明

本文把 OAuth scope 作为面向普通读者的教学模型。示例中的 scope 名称只用于说明粒度，不能替代各服务的正
式权限文档。
1. RFC 6749: The OAuth 2.0 Authorization Framework — §3.3 规定 scope 的表达、实际授予范围与客户端核对关系；§4.1 给出授权码流
程。

2. RFC 9700: Best Current Practice for OAuth 2.0 Security — 建议将访问令牌权限限制为具体应用/用例的最小需要，并限制受众、资源与
动作。

3. Google OAuth 2.0 Authorization — 展示获得、核对已授予范围、使用及刷新令牌的通用步骤，并建议在需要时增量请求。
4. Google: Handle granular permissions — 建议只请求完成任务的最小范围、检查实际授予范围，并让应用处理部分同意。
5. Model Context Protocol Authorization Specification — 将最小范围、增量升级、令牌受众验证和不足范围的 403 处理应用到 MCP 场
景。
