PKCE
Proof Key for Code Exchange

授权码被截获，为什么偷到的人仍换不到令牌？

PK
CE
核心一句话：PKCE 让客户端先留下一把一次性的秘密“钥匙”，只把它的指纹交给授权服务器；谁即使偷到了授权码，也无法证明自己握有原钥匙。

01 · 为什么这个概念重要

浏览器把“回执”交回应用时，路上并非永远只有好人

一个 AI 日历助手在手机或桌面端请求日历权限时，浏览器会在用户同意后带回一张短暂的授权码。问题在于，安装在设备上的其他应用或错误的回调处理者，可能拿到这张码。对不能可靠保守客户端密钥的公开客户端而言，PKCE 把“拿到授权码”从充分条件降为必要但不充分的条件。

它解决什么

阻断“截获授权码后抢兑令牌”

协议把一次授权交易与一个仅由发起客户端持有的随机秘密绑定。截获者虽然有授权码，却没有这份秘密，令牌端点应拒绝兑换。

没有它会怎样

短暂回执可能变成直接通行证

若授权码本身足以换令牌，错误的回调应用、日志泄漏或回调路径的拦截，都会把“用户刚刚同意”变成可被他人利用的机会。

事实 · 当代 OAuth 的基线RFC 9700 要求公开客户端使用 PKCE；对保密客户端也建议使用。它保护的是“授权码兑换”这一步，不是把所有 OAuth 风险一次清零。
02 · 一个直观类比

寄存柜回执 + 只在你口袋里的取件暗号

想象你把行李存进车站寄存柜。柜台先让你自己在手机里掷出一串随机暗号，你把暗号留在口袋里；柜台只记录它的不可逆“指纹”。之后柜台给你一张取件回执。有人半路捡走回执，也不能取走行李：他还得说出能算出同一指纹的原始暗号。

类比边界现实中的 code_verifier 不是人类口令，也不应被用户记忆或输入；它由客户端为每一次授权请求生成。哈希也不是万能封条：若原始随机值泄露、回调地址被错误信任，或令牌已经签发，仍需其他防护。

视觉一 · 寄存柜回执为何不够

阅读顺序：① 客户端留住暗号 → ② 服务器只收指纹 → ③ 回执可被截获 → ④ 没有暗号，无法取件。

图注：回执（授权码）可以经过不完全可信的回调链路；真正决定能否兑换的是回执与原始随机秘密能否配对。

看图结论：PKCE 不是藏起授权码，而是让授权码单独拿在手里也不够用。

03 · 一图看懂

先承诺一个“指纹”，后出示原始“钥匙”

PKCE 的关键不是加密所有内容，而是让服务器在授权开始时收到一个可比对的承诺值，在兑换时再验证发起方是否真正持有对应的原始值。

视觉二 · 输入 → 绑定 → 核验 → 输出

阅读顺序：从左到右看六步；紫色信息可被服务器记录，绿色信息只在最终兑换时出现。

图注：同一交易的 code_challenge 与授权码被服务器绑定；Token Endpoint 收到 code_verifier 后重新计算并比较。

看图结论：截获者若只得到第④步的 code，缺少第⑤步的 verifier，便卡在第⑥步。

04 · 工作原理

六步把“谁先发起”变成可核验的事实

  1. 生成一次性秘密。客户端为这一次授权请求产生高熵随机字符串 code_verifier，并只在本地短暂保存。RFC 7636 为其规定 43–128 个未保留字符的格式范围。
  2. 生成可公开的挑战值。客户端计算 code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))，并声明 code_challenge_method=S256。哈希让授权请求不直接暴露原始秘密。
  3. 随授权请求一同送达。浏览器打开授权页时，code_challenge 与范围、回调地址等参数一起交给授权服务器；用户登录、审阅并同意授权。
  4. 服务器把挑战值和授权码绑在一起。服务器签发授权码时记录该交易的 challenge 与方法。授权码回到客户端的路径仍可能是值得保护的边界。
  5. 客户端请求兑换。客户端把授权码交给 Token Endpoint，同时提交最初保存的 code_verifier。
  6. 服务器重新计算并做等值比较。相等才继续签发 Access Token；不相等应返回 invalid_grant。这就是“持有原始随机值”的证明。
为什么优先 S256？RFC 7636 规定：能使用 S256 的客户端必须使用它；RFC 9700 进一步指出，当前 S256 是不会在授权请求中暴露 verifier 的挑战方法。plain 仅为兼容性而留，不应当作为默认选择。
05 · 关键术语

四个对象，别把“码”“钥匙”“令牌”混成一团

PKCE

专业：OAuth 的 proof-of-possession 扩展，用一个挑战值和后续验证者绑定授权码交易。

白话：让“拿到回执”还不够，必须出示事先藏好的钥匙。

易混淆：它不是登录方式，也不是 Access Token。

code_verifier

专业：客户端每次授权请求生成的高熵随机字符串，用于关联授权请求和令牌请求。

白话：只留在发起应用手里的原始一次性暗号。

易混淆：不是客户端长期密钥，也不应写入日志。

code_challenge

专业：由 verifier 派生、随授权请求发送、供服务器以后校验的值。

白话：暗号的“指纹”；服务器先收指纹，不收原暗号。

易混淆：不是加密后的 Access Token。

授权码（authorization code）

专业：授权端点返回的短暂中间凭据，客户端可用它请求令牌。

白话：授权成功的取件回执，仍须配合 verifier 才能兑付。

易混淆：它本身通常不是给 API 用的通行证。

06 · 一个真实应用案例

安装式 AI 日历助手连接 Google Calendar 的安全起步

设想一款安装在电脑上的“今日行程摘要”助手。用户点击“连接 Google Calendar”后，应用需要在系统浏览器中完成登录和同意页；Google 的安装应用 OAuth 文档将 PKCE 列为增强此流程安全性的机制，并要求每次授权请求生成唯一 verifier 和对应 challenge。

协议事实

Google 文档中的 PKCE 参数

应用先生成 verifier 与 S256 challenge，在授权请求中发送 code_challenge；Token Endpoint 兑换时再提交 code_verifier 与授权码。

教学推演

助手为何受益

如果系统回调意外被别的本地程序抢先接收，它即使看到了 code，也不能仅靠 code 换取日历访问令牌；原助手持有的 verifier 仍是兑换所需的另一半。

说明：这是根据 Google 的安装应用 OAuth 文档构建的教学系统案例，不宣称任何特定 AI 日历产品使用完全相同的架构、回调方式或令牌生命周期。

图注：这些机制可以组合使用，但每个机制覆盖的对象与时段不同。

看图结论：PKCE 的核心岗位在“拿授权码换令牌”之间；不要期待它独自承担权限、会话和令牌防盗的全部工作。

概念主要回答的问题与 PKCE 的关系不能替代
Client secret保密客户端怎样向授权服务器证明客户端身份？公开客户端无法可靠保密它；PKCE 用每次交易的随机 verifier 补上“实例持有证明”。保密客户端也推荐用 PKCE。PKCE 的逐笔交易绑定。
state这次回调是否属于同一个浏览器会话？应用要恢复什么页面状态？两者都关联授权交易，但对象不同。PKCE 绑定 code 与 verifier；state 常承载会话关联和应用状态。正确校验回调、保存应用状态。
Access Token谁可以对 API 做已获授权的调用？PKCE 是取得它之前的一道兑换保护；Token 是拿到后的 API 凭据。令牌过期、受众限制、资源服务器校验。
DPoP已签发的访问令牌被偷后，怎样降低可重放性？PKCE 不保护已签发 Token 的每次 API 调用；DPoP 是后续持有者绑定思路。授权码兑换阶段的 PKCE。
08 · 常见误区

四句听起来合理的话，分别漏了什么

常见说法：有 HTTPS，就不需要 PKCE。
实际情况
HTTPS 很关键，但不能取代 PKCE。
为什么
PKCE 的设计针对授权码在设备内部应用间通信、回调处理等环节被截获后的兑换风险；TLS 保护的是网络传输，并不自动证明拿 code 的人就是原始发起客户端。
常见说法：授权码是一次性的，偷到也没关系。
实际情况
一次性不等于只能由正确的人使用。
为什么
没有 PKCE 时，先拿 code 去兑换的攻击者可能抢在合法客户端之前获得 Token。PKCE 要求兑换者还握有 verifier。
常见说法：PKCE 就是把授权码加密了。
实际情况
PKCE 不是加密授权码。
为什么
它让服务器在授权开始时保存 challenge，并在兑换时验证 verifier；安全性来自一次性随机值的持有证明和交易绑定。
常见说法：用了 PKCE，state、回调地址校验和 Token 保护都可以省掉。
实际情况
这些控制各有职责，常需组合使用。
为什么
PKCE 集中保护授权码兑换；应用状态、回调 URI、范围、访问令牌泄漏与撤销仍是不同的攻击面。
09 · 现实限制与风险

PKCE 很必要，但它不是 OAuth 的“免疫针”

随机性与保存：verifier 必须不可预测且不被写入日志、分析事件或不安全存储。若攻击者同时得到 verifier 与 code，PKCE 的屏障就消失。

挑战方法与降级：应优先 S256，并由服务器正确绑定 challenge、方法和 code。RFC 9700 要求服务器防范“把有 PKCE 的请求降成无 PKCE 流程”的实现缺陷。

不覆盖已签发令牌：一旦 Access Token 已到手，PKCE 不会阻止它被复制和重放；短生命周期、受众限制、发送者约束、最小 scopes 与撤销机制仍重要。

不替代用户判断：用户仍可能授权给钓鱼应用，或批准过宽的权限。PKCE 解决的是“正确授权过程里的 code 被抢兑”，不是“谁值得授权”。

10 · 三句话总结

把这三句带走

01

PKCE 是授权码流程的一次性持有证明：有 code 还不够，还要有最初生成的 verifier。

02

客户端先发送 verifier 的挑战值，兑换时才发送 verifier；S256 是应优先使用的方法。

03

PKCE 保护兑换前的授权码，不替代 HTTPS、回调校验、最小权限或已签发 Token 的防护。

11 · 三道理解题

确认你能迁移这套直觉

1. 一句话题：为什么说 PKCE 让授权码“单独不够用”？
参考答案：因为兑换 Token 时还必须提交与授权开始时 challenge 匹配的原始 verifier；截获者通常只有 code，没有 verifier。
2. 流程题：把下列对象放到正确时点：code_verifier、code_challenge、authorization code、Access Token。
参考答案：先在客户端生成 verifier，再计算并发送 challenge；用户同意后服务器返回 authorization code；客户端提交 code + verifier，服务器校验后才发 Access Token。
3. 迁移题：你的桌面 AI 文档助手通过系统浏览器连接云盘。恶意程序抢到了浏览器回调中的 code。开发者应该依赖“这个 code 只用一次”，还是让授权流程使用 PKCE？还要检查什么？
参考答案：应使用 PKCE，令恶意程序缺 verifier 无法兑换；还应使用 S256、保护 verifier、不记录敏感参数、严格注册/校验回调 URI、最小化 scopes，并保护最终获得的 Access Token。

13 · 来源与说明

把事实、类比与推演分开

  • RFC 7636 — Proof Key for Code Exchange by OAuth Public Clients：PKCE 的威胁模型、code_verifier/code_challenge、S256 公式、参数绑定与校验规则。
  • RFC 8252 — OAuth 2.0 for Native Apps：原生应用回调拦截风险与 PKCE 的使用背景。
  • RFC 9700 — Best Current Practice for OAuth 2.0 Security：公开客户端使用 PKCE、S256 与降级攻击防护的当代安全建议。
  • Google for Developers — OAuth 2.0 for iOS & Desktop Apps：安装应用中生成 verifier/challenge、授权请求与 Token 请求参数的现实文档案例。

事实：协议要求、公式、参数长度范围和 OAuth 机制均以上述一手规范/官方文档为依据。
类比：“寄存柜回执与暗号”仅用于建立直觉，不等同于密码学实现。
推演：“AI 日历/文档助手”是教学系统故事，用来说明 PKCE 在可安装 AI 工具连接外部服务时的角色，不代表具体产品声明或安全保证。
