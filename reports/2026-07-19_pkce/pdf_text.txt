只有好人

 事实 · 当代 OAuth 的基线
 RFC 9700 要求公开客户端使用 PKCE；对保密客户端也建议使用。它保

02 · 一个直观类比

寄存柜回执 + 只在你口袋里的取件暗号
想象你把行李存进车站寄存柜。柜台先让你自己在手机里掷出一串随机暗号，
你把暗号留在口袋里；柜台只记录它的不可逆“指纹”。之后柜台给你一张取件
回执。有人半路捡走回执，也不能取走行李：他还得说出能算出同一指纹的原
始暗号。


 类比边界

 由客户端为每一次授权请求生成。哈希也不是万能封条：若原始随机值泄
 露、回调地址被错误信任，或令牌已经签发，仍需其他防护。

04 · 工作原理

六步把“谁先发起”变成可核验的事实
1        生成一次性秘密。客户端为这一次授权请求产生高熵随机字符串
          code_verifier ，并只在本地短暂保存。RFC 7636 为其规定 43–

         128 个未保留字符的格式范围。

2        生成可公开的挑战值。客户端计算 code_challenge = BASE64URL-
         ENCODE(SHA256(ASCII(code_verifier))) ，并声明

          code_challenge_method=S256 。哈希让授权请求不直接暴露原始秘

         密。

3        随授权请求一同送达。浏览器打开授权页时， code_challenge 与范
         围、回调地址等参数一起交给授权服务器；用户登录、审阅并同意授
         权。
4       服务器把挑战值和授权码绑在一起。服务器签发授权码时记录该交易
        的 challenge 与方法。授权码回到客户端的路径仍可能是值得保护的
        边界。

5       客户端请求兑换。客户端把授权码交给 Token Endpoint，同时提交最
        初保存的 code_verifier 。

6       服务器重新计算并做等值比较。相等才继续签发 Access Token；不
        相等应返回 invalid_grant 。这就是“持有原始随机值”的证明。




    为什么优先 S256？
    RFC 7636 规定：能使用 S256 的客户端必须使用它；RFC 9700 进一
    步指出，当前 S256 是不会在授权请求中暴露 verifier 的挑战方法。
    plain 仅为兼容性而留，不应当作为默认选择。

09 · 现实限制与风险

PKCE 很必要，但它不是 OAuth 的“免疫针”
 随机性与保存：verifier 必须不可预测且不被写入日志、分析事件或不安全
 存储。若攻击者同时得到 verifier 与 code，PKCE 的屏障就消失。


 挑战方法与降级：应优先 S256 ，并由服务器正确绑定 challenge、方法和
 code。RFC 9700 要求服务器防范“把有 PKCE 的请求降成无 PKCE 流程”
 的实现缺陷。


 不覆盖已签发令牌：一旦 Access Token 已到手，PKCE 不会阻止它被复制
 和重放；短生命周期、受众限制、发送者约束、最小 scopes 与撤销机制仍
 重要。


 不替代用户判断：用户仍可能授权给钓鱼应用，或批准过宽的权限。PKCE
 解决的是“正确授权过程里的 code 被抢兑”，不是“谁值得授权”。

11 · 三道理解题

确认你能迁移这套直觉

 1. 一句话题：为什么说 PKCE 让授权码“单独不够用”？

 参考答案：因为兑换 Token 时还必须提交与授权开始时 challenge 匹配的原始
 verifier；截获者通常只有 code，没有 verifier。




 2. 流程题：把下列对象放到正确时点： code_verifier 、
  code_challenge 、authorization code、Access Token。


 参考答案：先在客户端生成 verifier，再计算并发送 challenge；用户同意后服务器
 返回 authorization code；客户端提交 code + verifier，服务器校验后才发 Access
 Token。




 3. 迁移题：你的桌面 AI 文档助手通过系统浏览器连接云盘。恶意程序抢
 到了浏览器回调中的 code。开发者应该依赖“这个 code 只用一次”，还
 是让授权流程使用 PKCE？还要检查什么？

 参考答案：应使用 PKCE，令恶意程序缺 verifier 无法兑换；还应使用 S256、保护
 verifier、不记录敏感参数、严格注册/校验回调 URI、最小化 scopes，并保护最终
 获得的 Access Token。

  • RFC 7636 — Proof Key for Code Exchange by OAuth Public
   Clients：PKCE 的威胁模型、 code_verifier / code_challenge 、
   S256 公式、参数绑定与校验规则。

  • RFC 8252 — OAuth 2.0 for Native Apps：原生应用回调拦截风险与
   PKCE 的使用背景。

  • RFC 9700 — Best Current Practice for OAuth 2.0 Security：公开客
   户端使用 PKCE、S256 与降级攻击防护的当代安全建议。

  • Google for Developers — OAuth 2.0 for iOS & Desktop Apps：安装
   应用中生成 verifier/challenge、授权请求与 Token 请求参数的现实文
   档案例。
