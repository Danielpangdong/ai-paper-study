DPoP：持有证明

Demonstrating Proof of Possession

如果 AI 助手的 Access Token 被复制走，光有那串字符的人为什么不该立刻获得权限？DPoP 给令牌加上“只能由持有另一把私钥的人使用”的约束。

核心一句话：DPoP 让客户端在每次请求时用私钥签一份只针对这次请求的证明；服务端确认令牌与这把钥匙绑定后，单独偷走令牌的人通常无法重放它。
OAuth Scopes→Access Token→Refresh Token→PKCE→Token Revocation→DPoP→Token Introspection
01 · 为什么重要、没有它会怎样

Bearer Token 的便利，也正是它的软肋

很多 Access Token 是 Bearer Token（持有者令牌）：谁拿到那串值，谁就能带着它调用被允许的 API。HTTPS 会保护传输，但它不能自动修复日志误收、内存泄露、错误复制、恶意浏览器扩展等“令牌已经离开原客户端”的事故。

DPoP 解决什么

把 Access Token（以及公共客户端的 Refresh Token）绑定到一对公私钥。令牌使用者除了提交令牌，还要针对这一次 HTTP 请求给出私钥签名的证明；只有复制令牌、没有私钥的人会卡在这一步。

没有它会怎样

资源服务器若只检查 Bearer Token 是否有效，复制者可在令牌到期或被撤销前直接重放。DPoP 不会消灭泄露，却把“偷到一个字符串就可用”改成“还得持有对应私钥”。

标准事实RFC 9449 将 DPoP 定义为 OAuth 2.0 的应用层 sender-constraining（发送者约束）机制，用于检测 Access Token 与 Refresh Token 的重放攻击；OAuth Security BCP 建议授权服务器和资源服务器使用 DPoP 或 mTLS 等机制，减少被盗令牌的滥用。
02 · 贯穿类比与边界

把令牌想成“提货单”，DPoP 想成每次取货都要盖的私章

小林让一个 AI 助手整理云盘文件。普通提货单写着“可取 A 仓的文件”；谁捡到纸就可能领货。DPoP 的做法是：发单时把提货单登记到小林的专用私章上；每次取货，助手都得在当日、该仓、该动作的回执上盖章。仓库会核对：提货单绑定的章，和这张回执的章，是不是同一把。

类比边界私钥不是绝对不可盗的实体印章。若攻击者同时拿到令牌和私钥，或能在客户端内以恶意代码实时生成证明，DPoP 的保护会被削弱。DPoP 也不是身份认证、权限审批或数据加密的替代品。

04 · 工作原理 6 步

DPoP 不是给令牌再加一段密码，而是改变验证问题

客户端生成一对密钥

专业：客户端选择一对非对称密钥，并把公钥以 JWK 形式放入证明，私钥用于签名。
白话：做一枚公开可验、但只有自己能盖的私章。私钥应放在系统安全存储或受保护模块中。

取 Token 时发送 DPoP proof

客户端向 Token Endpoint 请求 Access Token 时，在 DPoP HTTP header 放入私钥签名的 JWT。证明会写明 HTTP 方法 htm、目标 URI htu、签发时间 iat 与唯一编号 jti。

授权服务器把 Token 绑定到公钥

服务器验证证明后，把新发的 Token 与这把公钥关联，并用 token_type=DPoP 告诉客户端：它不是可被随意拿去重放的 Bearer Token。

每次调用 API 都生成一份新的证明

客户端带上 DPoP-bound Access Token，并为本次 HTTP 方法和目标 URI新签一份 proof。访问资源时，proof 还会放入 Access Token 的哈希 ath，把“这份签名”与“这张令牌”连在一起。

资源服务器做四类核验

它验证签名是否能被 proof 中的公钥验过、proof 是否指向当前方法与 URI、时间和唯一编号是否可接受、以及这把公钥是否正是 Token 绑定的那一把。任一关键检查失败，就不应授予资源。

必要时用 nonce 缩小预计算窗口

服务器可给出不可预测的 DPoP-Nonce，要求客户端在下一份 proof 中带回。它尤其用于降低恶意脚本提前生成大量 proof 后再外传的风险；收到 use_dpop_nonce 后，客户端应按服务端要求重试。

05 · 关键术语：专业 / 白话 / 易混淆点

四个词，分别守住不同的边界

Sender-constrained Token 发送者约束令牌

专业解释：令牌只对能证明掌握特定秘密或私钥的发送者有效。
白话解释：门票写着“必须由持有指定私章的人使用”。
易混淆点：它不等于 Token 加密；它仍需配合正常的签发、过期、撤销和权限检查。

DPoP Proof JWT 持有证明 JWT

专业解释：客户端以私钥签名、放在 HTTP DPoP header 中的 JSON Web Token。
白话解释：针对这一次取货写的、可验真伪的盖章回执。
易混淆点：它不是 Access Token 本身；每个 HTTP 请求都需要新的 proof。

ath Access Token Hash

专业解释：DPoP proof 中对当前 Access Token 的 SHA-256 哈希的 base64url 编码。
白话解释：回执上印着这张提货单的指纹，不能随手换成另一张。
易混淆点：ath 不替代方法、地址、时间等检查；只验哈希仍不足以防重放。

Nonce 服务端一次性挑战值

专业解释：服务器给客户端的不可预测值，客户端要纳入后续 DPoP proof。
白话解释：仓库临时指定的当日口令。
易混淆点：它不是 OAuth/OIDC 中所有“nonce”的统称；哪个服务器发的，只能回给哪个服务器。

06 · 一个有来源的真实应用

Okta 的跨组织自动化：让服务应用的 API 调用启用 DPoP

官方文档事实Okta 的 Org2Org 多租户 OAuth 2.0 配置说明，把一个组织中的服务应用作为 OAuth 客户端、另一个组织作为资源/授权端，并列出“为该 OAuth 2.0 客户端启用 DPoP”作为配置步骤。其示例配置将 dpop_bound_access_tokens 设为 true。

产品语境

跨组织的用户/组同步是后台服务代表组织调用 API 的场景。它既需要 scopes 和管理角色限制能做什么，也可能需要 DPoP，降低某个 Access Token 被复制后在别处重放的风险。

不能过度推断

教学推断该文档证明产品支持并指导启用 DPoP；本文不据此声称所有 Okta API、所有应用、所有请求默认都使用 DPoP。具体支持面、密钥托管和失败处理应以部署时的当前官方配置为准。

07 · 相近概念对比

PKCE、DPoP、撤销：各自看守不同的时间点

概念它要回答的问题最容易混淆的边界
Bearer Token“谁出示令牌，谁能使用？”答案是任何持有者。HTTPS 保护传输，不会让泄露后的令牌自动失效。
PKCE“截获授权码的人怎样不能把它换成 Token？”它主要保护授权码到 Token 的兑换，不是 Access Token 的使用证明。
DPoP“Token 已发出后，怎样让复制者缺少关键材料？”它不单独作认证/授权决定，也不等于私钥永远不会被盗。
令牌撤销“不想再授权时，怎样提前收回？”它负责止损，不会让已复制的数据自动删除。
08 · 至少三个误区

DPoP 增加了一层验证，不等于给系统开了无敌模式

误区 1：DPoP 把 Token 加密了，所以泄露也无妨。

纠正：DPoP 的核心是发送者约束和私钥签名，不是把 Access Token 本身加密。令牌仍应避免泄露，仍需最小权限、短寿命和撤销策略。

误区 2：有了 DPoP proof，就不必校验 Access Token。

纠正：proof 只证明某把私钥的持有，以及它与这次请求的关系；RFC 9449 明确说 proof 本身不足以做访问控制决定。Token 的签名、过期、受众、scope 和撤销状态仍须检查。

误区 3：同一份 proof 可以安全地多次使用。

纠正：每个 HTTP 请求需有唯一 proof。jti、时间窗口、方法与 URI 让服务端有机会发现/拒绝重放；服务端也可能用 nonce 强化这一点。

误区 4：DPoP 能防住已被接管的客户端。

纠正：若攻击者可同时获取私钥、或在客户端运行恶意代码实时签名，DPoP 的发送者约束会被突破。它主要提高“仅 Token 泄露”的攻击成本。

09 · 限制、风险与适用边界

是否该上 DPoP，取决于风险、客户端形态与端到端支持

私钥保护是地基

DPoP 的价值来自“私钥没随 Token 一起泄露”。客户端应优先使用受保护的密钥存储；密钥轮换、遗失恢复、备份策略也要设计，否则会变成新运维负担。

资源端必须一起升级

授权服务器能发 DPoP-bound Token，不代表所有资源服务器都会正确验证。混合 Bearer/DPoP 部署尤其要防降级：支持两者的资源端应拒绝把 DPoP-bound Token 当 Bearer 接受。

需要可观察性但不能记秘密

服务端要处理时钟偏差、jti 重放窗口、nonce 重试与签名算法；但日志、监控、错误上报不应记录 Access Token、DPoP proof 或私钥材料。

安全边界RFC 9700 指出：攻击者若同时获得令牌和密钥材料，发送者约束会被破坏；浏览器中的 XSS 和被攻陷的客户端是特别重要的威胁。因此 DPoP 应与 CSP/XSS 防护、最小权限、短期 Token、刷新令牌轮换/绑定、撤销和审计一并使用。
10 · 三句话总结

把今天的概念压缩成三句

  1. DPoP 让 OAuth Token 绑定到一对密钥：拿 Token 还不够，使用时还得证明持有相应私钥。
  2. 客户端为每次 HTTP 请求生成新的、签了方法、地址、时间和唯一编号的 DPoP proof；资源服务器检查它与 Token 的公钥绑定是否一致。
  3. 它主要降低只有 Token 被复制时的重放风险；若 Token 与私钥一起失守，或客户端被实时控制，仍要靠其他安全层止损。
11 · 三道理解题及答案

用自己的话检查是否真正理解

1. 一句话题

DPoP 相比 Bearer Token，多要求了什么？

参考答案：除了提交 Token，客户端还要用与 Token 绑定的私钥，为这次 HTTP 请求签一个 DPoP proof；只有 Token 的复制者通常做不到。

2. 边界题

攻击者偷到了 Access Token 和用户设备中的私钥，DPoP 一定能阻止他吗？

参考答案：不一定。DPoP 的关键假设是攻击者没有对应私钥；两者同时泄露或攻击者能在客户端内实时签名时，发送者约束会被削弱。

3. 迁移题

为什么 DPoP 不能替代 PKCE 和 Token Revocation？

参考答案：PKCE 防的是授权码被截获后兑换 Token；DPoP 防的是已发 Token 被单独复制后重放；撤销则用于不再授权或发生风险后提前收回。三者覆盖不同时间点。
12 · 知识地图增量

今天在 OAuth 课程里补上哪一块

继承

OAuth Scopes 定义“允许做什么”；Access Token 是调用 API 的凭据；Refresh Token 支持续发；PKCE 保护授权码兑换；令牌撤销负责提前收回授权。

今日新增

DPoP 把焦点放在令牌已经发出之后的呈示：客户端怎样证明“正在用这张 Token 的仍是原来的密钥持有者”。

被修正

“HTTPS + Token”并不等于泄露后无风险；也不能把“有 DPoP proof”误当作身份、权限与资源策略都已通过。

后续候选

Token Introspection：资源服务器怎样在线问 Token 是否仍有效；Authorization Server Metadata：客户端怎样发现服务器是否支持 DPoP；mTLS-bound Tokens：另一种发送者约束路径。

13 · 来源账本

关键事实可回到标准与官方产品文档

  1. RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP)：DPoP 的定义、proof JWT 字段、Token/公钥绑定、ath、nonce、资源端核验、DPoP/Bearer 兼容与降级风险。
  2. RFC 9700 — Best Current Practice for OAuth 2.0 Security：发送者约束建议、公共客户端 Refresh Token 的绑定/轮换要求、密钥材料同时泄露时的边界。
  3. RFC 7636 — Proof Key for Code Exchange by OAuth Public Clients：与 DPoP 相邻的 PKCE 概念，用于说明它保护的是授权码兑换而非 Token 呈示。
  4. Okta Developer — Secure API connections between orgs with OAuth 2.0：Org2Org OAuth 配置中启用 DPoP 以及 dpop_bound_access_tokens 的实际产品文档。
  5. OpenID Foundation — FAPI 2.0 Security Profile（Final, 2025）：面向高价值 API 的 sender-constrained Token 获取与安全使用语境。
