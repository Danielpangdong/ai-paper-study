AI 怎么被允许替你调用外部服务？

核心一句话：访问令牌是一张由授权服务器签发、带着权限和有效期的“限时工
作证”；应用拿它向 API 办事，而不是拿走你的密码。
系统提示词

→ 最小权限 → OAuth Scopes → Access Token → PKCE → Refresh Token

01 · 为什么这个概念重要

让应用能做事，又不必知道你的密码

AI 助手要“读取日历后帮我排下周计划”，必须访问日历 API。最粗暴的办法是把账号密码
交给它；这会让密码被复制、难以只授权一项能力，也难以单独撤销。访问令牌把“登录
身份”与“某个应用可做的事”拆开。
它解决什么

把授权变成可控制的凭证

令牌可被限制在某些资源、动作和时长。用
户撤销一个应用的授权时，不必改密码、也
不必踢掉所有设备。
事实 · 协议给出的定义

没有它会怎样

每个第三方都想要“总钥匙”

应用需要保存密码，权限往往过大；一处泄
露可能波及整个账户。OAuth 的目标正是
让第三方拿到不同于用户密码的一组凭证。

OAuth 将 access token 定义为访问受保护资源的凭证：它代表已授予客户端的授权，通常对客
户端是不可读的字符串；具体的范围、时长与格式由系统设计决定。

应用提出最小任务。例如“读取本周日历”，而不是笼统地要求所有账号权限。这里会用
scope 描述希望访问的资源和动作。
用户在授权服务器处登录并同意。密码只交给用户信任的授权服务器；AI 应用不应看到或保
存它。
授权服务器签发访问令牌。它把“谁授权给哪个客户端、在什么范围和时段内能做什么”变成
可核验的凭证。令牌对客户端通常只是一个不透明字符串。
客户端把令牌放进 API 请求。常见做法是放在 Authorization: Bearer … 请求头中，
而不是拼到 URL 里，以减少进入日志、历史记录的机会。
资源服务器验票。它检查令牌是否仍有效、是否面向本服务、是否涵盖这次动作；具体实现
可能本地验证，也可能向授权服务器查询令牌状态。
按结果返回数据或拒绝。验证通过，API 才返回相应资源；令牌过期、范围不足或目标服务
不匹配，都应被拒绝。

推断 · 对 AI Agent 的意义

“能调用工具”不等于“应当放行所有工具”。Access token 把模型的文字意图，落到外部系统可
执行、可收回、可审计的权限边界上；但它不能替代业务审批与操作确认。

06 · 一个真实应用案例

“帮我总结本周日程”的日历助手

这不是让 AI 获取用户 Google 密码。一个日历助手可以把用户带到 Google 的授权页面，请求日历
所需范围；用户同意后，应用收到访问令牌（或先收到授权码再换取令牌），并用令牌在请求头中调
用 Calendar API。Google 的官方 OAuth 指南明确区分：令牌只对相应 scope 描述的操作和资源有
效；发给 Calendar API 的令牌并不因此获得 Contacts API 的权限。

允许的链路

仍需额外设计

任务 → 授权 → 读取 → 总结

写入必须更谨慎

AI 读取用户已授权的日程，生成“冲突提
醒”和“空档建议”。它把“理解文字任务”的
能力与“访问日历”的能力分开。

“读取后总结”不等于“可以创建、删除或邀
请他人”。对改动日历的动作，产品还应加
入清晰的预览、确认和撤销机制。

说明：这是基于 Google 官方 OAuth 与 Calendar API 机制的系统级案例，并非声称某一特定 AI 产品目前采用完全相同的
实现。

08 · 常见误区

四个看似合理、其实危险的说法
常见说法：“有 token 就等于登录了。”

实际情况：Access Token 的核心是授权 API 调用；“你是
谁”的身份信息是另一层问题，常由 OpenID Connect 的 ID
Token 等机制处理。

为什么：“身份”与“对某资源的授权”可以相关，但不应该混成一张万能通行证。

常见说法：“令牌长得像 JWT，就能自己信。” 实际情况：Access Token 可以是不可读的随机字符串，也
可以是可验证的结构化令牌；资源服务器仍要按发行方、
签名、时效、受众和权限等规则验证。
为什么：格式只是包装；能否放行取决于系统核验与策略。

常见说法：“令牌放 URL 里更方便。”

实际情况：官方实践通常使用 Authorization 请求头。URL
参数可能进入浏览器历史、代理或日志，扩大泄露面。

为什么：常见 bearer token 被谁拿到谁就可能使用。

常见说法：“scope 是 read，就一定万无一
失。”

实际情况：scope 是重要边界，但服务端仍应校验资源、
动作、受众和自身业务规则；“读取”也可能包含高度敏感的
数据。

为什么：最小权限是在减少损害面，不是在制造绝对安全。

09 · 现实限制与风险

令牌缩小风险，却不会自动消除风险
Bearer Token 泄露与重放

最常见的 bearer token 是“持有即可使用”的凭证。它若被截获，攻击者可能重放请求。因此应避
免写入日志或 URL，使用 TLS，并限制寿命和权限。更高风险系统还可使用 DPoP 或 mTLS 等
“绑定持有者”的机制。

“可读”本身也可能太多

访问令牌把权限划小，但 scope 的粒度取决于服务商。一个宽泛的读取范围，可能仍让应用看到
大量隐私信息；产品要在功能便利与最小收集之间取舍。

令牌不能替代人的确认

如果 AI 能调用“发邮件”“转账”“删除文件”工具，令牌只能证明技术层面允许调用。高影响动作仍
应有清晰的用户确认、预算/额度、审计日志和撤销路径。

令牌状态是动态的

它可能过期、被撤销、范围被收回，或不适用于另一个 API。应用不能把一次成功当作永久成
功，而要正确处理拒绝与重新授权。

11 · 三道理解题

检查你是否真的掌握了
1. 一句话题

为什么日历助手应该请求 Access Token，而不是要求用户给出账号密码？
参考：令牌能把授权限制在特定操作、资源和时段，并可以单独撤销；密码通常权限更大，也不应交给第三
方应用保存。

2. 区分题

Access Token、ID Token、Refresh Token 分别最应该交给谁？
参考：Access Token 给资源服务器/API；ID Token 给客户端应用用于身份信息；Refresh Token 给授权服务
器以换取新的 Access Token。

3. 迁移题

一个 AI 助手只需“读取文档并做摘要”，却请求了“读取、创建、删除全部文件”的长期令牌。你
会建议哪些改动？
参考：改为仅覆盖读取所需资源的最小 scope，缩短 Access Token 的生命周期，避免把令牌写入日志；对
创建/删除另行按需授权并加用户确认，提供撤销入口。

13 · 来源与说明

关键事实来自标准与官方文档

1. RFC 6749 — The OAuth 2.0 Authorization Framework：OAuth 的角色、抽象流程、Access
Token 定义，以及它可以是不透明标识或可验证信息的说明。
2. RFC 6750 — Bearer Token Usage：持有 bearer token 的一方可使用它；应保护其在存储和传
输中的机密性。
3. RFC 7662 — Token Introspection：令牌状态、scope 等信息的受保护查询机制与 inactive 语
义。
4. RFC 9700 — OAuth 2.0 Security BCP：当前 OAuth 安全实践；令牌最小权限、受众限制、资
源服务器逐次核验与 token replay 防护建议。
5. Google OAuth 2.0 Authorization：应用取得令牌、检查已授予范围、通过 Authorization 请求
头调用 Google API，以及令牌与 refresh token 的实践流程。

说明
本文用“日历读取”“限时工作证”等例子教学，不代表所有 OAuth 服务使用同一组 scope 名称、
相同令牌格式或相同时长。具体实现以对应授权服务器和 API 的官方文档为准。
